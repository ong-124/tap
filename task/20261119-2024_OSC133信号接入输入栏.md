# 任务：OSC 133 信号接入输入栏

## 背景与目标

20261119 架构讨论将 OSC 133 只读上报列为「未来候选」，用户拍板采纳。源码核查后**事实修正：协议层已全量存在**（upstream tap 继承，非待建）——本任务是消费侧接线，把已经在流的信号接进输入栏功能。同时修正既有认知：此前架构讨论以为「不碰 shell」是现状，实际 upstream tap 从 spawn 起就自动注入集成脚本，哲学分歧不存在，只剩消费问题。

## 现状盘点（20261119-2024 核查）

| 层 | 现状 | 位置 |
|---|---|---|
| 注入 | spawn 自动注入：zsh 走 `ZDOTDIR`（原值存 `TAP_ZSH_ZDOTDIR`、用户配置运行前恢复）、fish 走 `XDG_DATA_DIRS` prepend（脚本内还原）、PowerShell 重写 argv；`TAP_SHELL_INTEGRATION` 供任意 shell 手动 source；bash/cmd 不注入；旧版本脚本目录刻意保留（防并发旧实例 ZDOTDIR 悬空） | `frontends/tapterm/src/shell_integration/mod.rs` |
| 脚本 | zsh：每次提示符/目录变化发 OSC 7 cwd（kitty-shell-cwd 风格）+ OSC 133 A/B/C/D；fish 4 原生自发标记 | 同目录 `tap-integration.zsh` / `tap.fish` |
| 解析 | OSC 133 `A`/`N`/`C`/`D`（D 带 exit status，`N` 先闭合未闭命令再开提示符）；OSC 7 与 OSC 9;9 cwd 均分发 | `tap-vt/src/performer/handler.rs:1024,1071-1093` |
| 状态 | pane 级 `current_directory: Option<PathBuf>`（变更去重、发事件） | `tap-vt/src/crosswords/mod.rs:591,3927` |
| 事件 | `CommandFinished { exit_status, duration, route_id }` 一路到 tapterm application 层 | `tap-vt/src/event/mod.rs:302`、`frontends/tapterm/src/application.rs:221` |
| 消费 | **仅** notify-on-command-finish 通知（时长阈值 + unfocused 判定） | `application.rs:230` |

结论：信号链完整，输入栏侧（历史库/补全/建议）零消费。

## 接线设计

### 接线一：exit code 落历史库

- 提交侧（`screen/mod.rs` submit 路径）：append 三列照旧，同时在内存记 `pending_exit: (route_id, ts, line)` 最近一条（每 pane 一条即可，覆盖式）
- 完成侧（`application.rs handle_command_finished`）：按 route_id 匹配 pending → TSV 该行回填第四列 exit（低频全文件重写，与 20261119-2003 任务 P2 的重写机制共用；万条内 <5ms）
- 格式：`{ts}\t{cwd}\t{line}[\t{exit}]`，读侧兼容旧三列（exit 列缺失 = 未知）；`D` 不来（无标记 shell/崩溃）exit 永远空，行为退化为现状
- 消费场景暂为备料（将来：失败命令标记/重试/统计），本任务不做任何 UI 展示

### 接线二：cwd 真值替换探测

- Tab 补全 `Sources` 与历史 Entry 的 cwd 数据源改为：pane `current_directory`（OSC 7 真值）优先，`foreground_process_path` 探测降级为兜底（无标记 shell：bash、远端场景）
- 顺带服务 20261119-2003 任务 P3「ghost 同 cwd 优先」的取值
- 需确认 `current_directory` 在 pane 生命周期内的更新时机（每次提示符都会刷，ssh 进远端后仍报本地路径——**远端会话不更新**，须以探测兜底识别，与 1801 任务 ssh 探测逻辑对齐）

### 明确不做

- **锁定判定不动**：维持修复轮次八行为（仅 ALT_SCREEN 锁定）。教训存档：标记只做增强不做门控（zone 门控在 ssh 下永锁已移除），A/C 状态真值留作将来锁定精化的输入，本任务不碰
- bash/cmd 注入补齐、远端 ssh 标记（远端 zshrc 不归 tap 管）、exit code 的 UI 展示
- duration 元数据落盘（顺手可加列，非目标）

## 验收

- `cargo test` 全绿，clippy/fmt 干净
- 手测（用户执行，zsh）：提交命令后 `input-history` 尾行带第四列 exit（成功 0/失败非 0）；bash pane（无标记）行为不变三列；ssh 会话补全 cwd 仍正确（探测兜底）；notify-on-command-finish 不回归

## 实施记录（20261119-2109）

| 层 | 文件 | 内容 |
|---|---|---|
| 存储 | `input_history.rs` | `Entry` 增 `exit: Option<i32>`；encode/parse 支持可选第四列（尾部 `\t<整数>`，stray-tab 行尾恰为整数时误读为 exit 为已文档化边界）；`backfill_exit` 按 `(ts, line)` 匹配**最新**未回填行拼接 exit，其余字节逐字保留（cwd/坏行不再编码）；`exit_target` 纯函数按「命令起始时间」排水队列；`push_exit_candidate` 带 `MAX_EXIT_PENDING=8` 上限；测试 +8 |
| 匹配 | `screen/mod.rs` | Screen 增 `exit_pending: HashMap<route_id, VecDeque<(ts, line)>>`；`submit_input_bar_line` 落盘后入队（仅记录分支入队——重跑同命令被去重跳过时不入队，其 D 自然排空旧队）；`note_command_finished`：`started_at = now - duration`，exit_target 取目标回填，`D` 无状态也排水（防队头滞留） |
| 路由 | `application.rs` | `handle_command_finished` 顶部先调 `note_command_finished`（先于 notify 配置早退与 route 存活检查——pane 已关也照常排水回填） |
| cwd | `screen/mod.rs` | 新 `focused_pane_cwd()`：OSC 7 `current_directory` 优先（提示符与 chpwd 双时机刷新）、`foreground_process_path` 探测兜底、双无则 None；`input_bar_tab_complete` 与 `submit_input_bar_line` 换用（submit 的 Windows cfg 分支随之消并为 `unwrap_or_default`） |

实施偏差与修正：

- 事件链里**没有** `CommandStarted`（C 只在 tap-vt 内部计时用），原设想「C 确认制」不可行，改为纯时间窗排水；首版给窗口加了 +1 宽限，测试抓出它会把「命令运行中提交的下一行」错吸进窗口——提交必然先于命令启动，秒级取整不破坏该序，宽限删除（`exit_target_picks_the_newest_submission_before_the_start` 回归锁定）
- 同秒背靠背双提交（秒级 ts 无 `CommandStarted` 不可分辨）回填最新一条，至多错标一行 exit，已注释文档化
- cap 裁剪的 `rewrite` 重编码时丢 ts/cwd/exit 为存量行为，本次不动

验证：tap-backend 229 / tap-vt 708 / tapterm 373（新增 8）通过，clippy 无新告警，fmt 干净。
